# 이커머스 웹 서비스 검증

변경으로 영향을 받는 고객·운영자 흐름을 고르고, 화면이나 API 결과부터 저장 상태와 외부 효과까지 확인한다. 검증 계획 요청에는 재현 절차와 판정 기준을 작성한다. 실행 요청에는 프로젝트의 기존 테스트와 격리 환경을 사용하고, 테스트 추가나 구현 수정은 요청 범위에 맞춘다.

## 검증 범위와 근거

1. 변경 코드나 요구사항에서 시작해 실제 화면/API → 서비스 → DB·큐·외부 연동 경계를 따라간다. 현재 업무키, 허용 상태 전이, 금액·수량 산식, 권한, 재시도 조건을 코드와 제공된 계약·정책에서 확인한다. 기대 결과를 바꾸는 미확인 조건은 확인이 필요한 항목으로 남긴다.
2. 영향이 큰 정상 흐름과 실패·경계 사례를 짝지어 고른다. 각 사례에 초기 데이터, 요청 또는 이벤트 순서, 예상 화면/API 결과, 커밋 후 상태, 외부 효과의 횟수를 적는다. 경계 시간을 시험할 때는 설정된 업무 시간대를 확인하고 테스트 시계를 고정한다.
3. 사용하는 DB·큐·인증 설정과 외부 대역을 확인한 뒤 격리된 테스트 데이터로 실행한다. PG 샌드박스는 테스트 계정과 호출 범위가 승인된 경우에 사용한다. 운영 결제·환불·지급, 운영 데이터 변경, 실제 고객 대상 알림은 별도 승인 범위를 확인한다. 고객 정보·인증정보는 데이터와 결과 기록에 남기지 않는다.

## 변경에 맞는 사례

| 변경 영역 | 재현과 판정 |
|---|---|
| 장바구니·주문 | 결제 직전 가격·혜택·배송비가 바뀐 사례에서 유효한 견적이 유지되는 조건과 재확인·거절 조건을 제공된 정책으로 판정한다. 주문에 확정된 항목·금액과 화면/API에 표시된 값을 비교한다. |
| 재고 | 즉시 차감 정책에서 재고 1개, 서로 다른 유효한 주문 두 건, 다른 실패 요인 없음으로 시작한다. 두 요청이 경합한 뒤 성공 1건과 품절 1건인지 확인한다. 새 연결에서 잔여 재고 0개, 성공 주문에 귀속된 1개 차감 한 건을 대조한다. 모두 실패한 경우도 불합격이다. 예약형은 해당 정책의 확보·확정 시점에 맞춰 판정한다. |
| 쿠폰 | 마지막 발급권에 두 요청을 보내고 커밋 후 발급 원장에서 캠페인·사용자 한도를 확인한다. 메시지 소비 경로가 있으면 커밋 후 ack 전 실패를 일으켜 재전달 시 효과가 한 번만 남는지 본다. |
| 결제·웹훅 | 동일 키와 동일 요청의 재시도, 동일 키와 다른 요청의 충돌을 각각 재현한다. 승인 후 응답 유실과 중복·역순 웹훅에서 미확정 상태가 조회·대사로 수렴하고 승인·후속 효과가 중복되지 않는지 확인한다. 응답 규약은 PG·이벤트별 계약을 적용한다. |
| 부분 환불·반품 | 처리 중·미확정 시도가 점유한 금액과 주문 라인·개별 수량을 확인한다. 주문 총액 한도 안에서 같은 단위를 다른 키로 다시 요청해도 중복 확보가 없어야 한다. 실패 확정 뒤 해제와 혜택·재고의 실제 복원 시점은 제공된 정책으로 판정한다. |
| 배송·정산 | 같은 상태 통지를 재전달하거나 동일 대상 배치를 재실행해 출고·원장 반영·지급 효과의 중복을 확인한다. 주문·PG·내부 원장의 금액과 대상 건수를 대사하고 업무일 경계에서 누락을 확인한다. |
| 고객·판매자·관리자 화면 | 허용 사용자와 다른 소유자·판매자 역할의 합성 계정으로 같은 업무를 실행한다. 화면과 서버의 허용 결과, 응답에 포함된 정보, 데이터 변경 여부를 확인한다. |

## 테스트 수준과 결과

- 금액 계산·상태 전이는 단위 테스트, 트랜잭션·제약·동시성과 이벤트 재전달은 프로젝트의 격리 통합 테스트를 사용한다. 경합을 검증할 때는 독립된 연결이나 요청을 실제로 겹치게 하고 모두 종료한 뒤 커밋된 상태를 읽는다. 화면이 바뀌면 해당 사용자 흐름을 브라우저에서 확인하고 화면 결과와 백엔드 결과를 대조한다.
- 기존 인수 기준의 번호나 문구를 유지해 `인수 기준 | 사례 | 환경·명령 | 기대 | 관찰 | 결과`를 기록한다. 한 기준에 정상·거절 사례가 모두 필요하면 각각의 결과를 남긴다. 통과·실패·차단·미실행을 구분하고, 실패에는 재현 입력과 어긋난 금액·상태·효과를 붙인다. 현재 변경에서 실행한 근거가 없는 기준과 정책 미결로 기대값을 정할 수 없는 기준도 최종 리뷰에 전달한다.
- 판정에 필요한 사건이 발생했는지 확인한다. 예를 들어 주문과 차감이 모두 0건이면 고아 차감 0건은 관찰한 사실이다. 성공한 주문에 차감이 귀속되는지는 ‘미검증’으로 기록한다.
- 대역·실제 저장소·PG 샌드박스에서 확인한 범위를 명시한다. 배포 판정이 요청되면 출시를 막는 실패나 미확인 계약, 필요한 확인과 통과 기준을 제시한다.
