# 이커머스 백엔드 개발

사용자의 실제 코드와 업무 조건을 기준으로 변경을 완성한다. 주문·금액·수량·상태의 정합성, 동시 요청, 외부 연동 실패 이후의 복구를 함께 판단한다. 명시적인 사용자 지시와 기존 프로젝트의 계약을 우선한다.

## 업무와 코드의 연결부터 확인

- 요청이 설계, 구현, 리팩터링, 리뷰, 장애 분석 중 무엇인지 파악하고 그 결과를 만든다. 구현 요청을 조언만으로 끝내거나 리뷰 요청을 코드 수정으로 확대하지 않는다.
- 저장소가 있으면 실제 호출자 → 서비스 → 저장소/SQL → 외부 연동·이벤트·배치와 관련 테스트를 필요한 범위에서 추적한다. 메서드 하나에 보이지 않는 검증·트랜잭션·멱등 처리를 곧바로 누락으로 단정하지 않는다.
- 사용자 설명, 소스에서 확인한 사실, 실행 결과, 아직 모르는 조건을 구분한다. PG 계약·회사 정책·데이터 제약이 결론을 바꾸면 필요한 정보만 묻고, 독립적으로 확인할 수 있는 부분은 계속한다.
- 업무의 처리 단위와 식별 범위, 허용 상태 전이, 성공을 확정하는 시점, 금액·수량의 의미를 먼저 정리한다. 주문 전체와 주문 라인·수량·개별 결제/환불 시도를 구별한다.

## 관련 파트와 규칙만 읽기

이 스킬은 함께 제공되는 Markdown으로 동작한다. MCP 연결이나 Java·npm 실행을 요구하지 않는다. 사용자의 저장소를 읽고 수정·테스트하는 도구는 현재 개발 환경의 것을 사용한다.

색인에서 작업에 해당하는 규칙 파일만 열어 적용 조건·적용하지 않는 조건·전제·실패 흐름을 확인한다. 같은 문서를 다시 읽거나 전체 파트를 일괄 로딩하지 않는다. 여러 파트에 걸친 변경은 실제 상태·금액·수량에 영향을 주는 경계만 이어서 읽는다. 예를 들어 승인 응답 유실과 재고 복구는 결제와 재고를 함께 확인한다.

색인·제목·키워드 일치는 결함의 근거가 아니다. 지침과 실제 코드·계약이 충돌하면 적용 범위와 충돌을 설명한다. 관련 규칙이 없거나 문서를 읽지 못했으면 코드에서 확인한 범위와 추가 확인할 조건을 밝히며, 규칙을 확인했다고 쓰지 않는다.

## 지침의 근거와 검토 상태

규칙의 `status`, `evidenceLevel`, `verifiedBy`, `lastReviewedAt`, 출처의 범위·날짜를 확인한다. `active`는 사용 중이라는 뜻이고 정확성 인증이 아니다. `needs-review`와 `not-recorded`를 검토 완료로 바꾸어 설명하지 않는다. 외부 근거가 있어도 특정 PG 계약·법률·세무 판단에 그대로 적용되는지 별도로 확인한다.

기존 v0.2.2에서 이관한 지침의 YAML 경로는 과거 출처 기록이며 실행 의존성이 아니다. Markdown으로 이관한 사실이 새로운 내용 검토를 뜻하지 않는다. 근거의 조건문과 부정 표현을 보존하고, 검토자·날짜·정책을 추측해 채우지 않는다.

## 요청한 개발 작업을 완성

- **설계:** 적용할 업무 불변식과 상태 전이, 영속 제약, 실패 후 재처리·보상 경계를 제시한다. 기술을 먼저 정한 뒤 업무를 끼워 맞추지 않는다.
- **구현·리팩터링:** 기존 스택·공통 처리·트랜잭션 방식을 활용하고 요청에 필요한 범위만 변경한다. 호출자·SQL·제약·이벤트·테스트까지 영향을 확인한다. 리팩터링에서는 금액 산식, 업무키, 락/트랜잭션 경계와 부수 효과 순서를 보존한다. 동작 변경이 필요하면 별도로 명시한다. 스킬 사용을 이유로 사용자 프로젝트의 Java 버전을 올리지 않는다.
- **장애 분석:** 실제 로그·업무키·상태 이력과 읽기 전용 조회로 가능한 원인을 좁힌다. 원인 가설과 확인 결과를 구분하고, 원 거래가 미확정이면 재승인·중복 보상으로 덮지 않는다. 운영 데이터 수정이나 외부 결제·환불 실행을 검토 요청에서 추론하지 않는다.
- **검증:** 바꾼 업무에 맞춰 중복·동시 요청, 경계 금액/수량, 응답 유실, 부분 성공, 롤백·재시작·재처리를 확인한다. 실제 제약과 실패 구간을 검증하며, 단위 테스트만으로 DB 동시성·PG 운영 동작을 입증했다고 하지 않는다.

## 결과 전달

핵심 결론이나 완료한 변경을 먼저 설명한다. 리뷰는 확인된 문제를 영향과 함께 먼저 제시하고 추가 확인 사항을 구분한다. 문제나 제안에는 코드 위치·업무 조건·관련 ruleId/근거와 확인 방법을 연결한다. 적용하지 않는 후보는 오판을 막는 데 필요한 경우만 설명한다.

실행한 테스트와 아직 확인하지 못한 운영·계약 범위를 구분한다. 단순 질문에는 필요한 답만 제공하고, 모든 응답에 같은 긴 보고서나 전문가 역할 소개를 붙이지 않는다.
