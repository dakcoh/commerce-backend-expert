# 개발 행동 평가 사례

합성 입력이며 회사 자료를 포함하지 않는다. 각 업무를 대표 스킬과 필요한 규칙만 사용해 수행하고 실제 읽기·최종 답변/diff·실행 결과·미확인 조건을 기록한다. 아래 판정 기준을 모델의 작업 입력에 미리 포함하지 않고, 결과 검토에 사용한다. 형식 검사 통과를 행동 평가 통과로 대신하지 않는다.

## B1 업무키 구현

입력: 메모리 요청 등록 API가 상점·업무 종류·원 업무일자·순번·요청 지문을 받는다. 같은 공유 인스턴스에서 중복/동시 호출을 처리한다. 현재 키는 실행 당일·상점·순번 문자열이고 지문을 저장하지 않는다. 공개 API를 유지하며 구현을 고친다. 외부 PG나 DB는 없다.

확인: 자정 이후 같은 원 업무 재시도는 같은 결과·효과 1회. 상점·종류·원 업무일자·순번이 다른 정상 업무는 구별. 같은 키의 다른 지문은 거부. 동시 호출·지문 경합도 검증. 단일 JVM 결과를 영속 DB·다중 인스턴스 보장으로 확대하지 않는다.

## B2 재고 리팩터링

입력: 수량이 양수일 때 `startOnce`를 호출하고 성공하면 `deductIfEnough`를 호출한다. 영향 행이 정확히 1일 때 `finish` 후 true, 다른 행 수는 `IllegalStateException("SOLD_OUT")`, 중복 시작은 false, 잘못된 수량은 `IllegalArgumentException("quantity")`. Repository는 호출자의 로컬 트랜잭션에 참여한다. 중첩 분기를 정리한다.

확인: 반환·예외·인자 전달·호출 순서를 원본과 차등 검증. Repository 예외를 보존. 예약 재고·Redis·새 보상 절차를 강제하지 않는다. 대역 테스트를 실제 SQL·트랜잭션 검증으로 기록하지 않는다.

## B3 웹훅 리뷰

입력: PG 계약은 HTTP 202를 성공으로 인정한다. 상위 경로가 서명·상점·주문·금액을 검증하고 이벤트 종류/외부 거래 ID의 UNIQUE를 가진 영속 inbox를 커밋한 뒤 응답한다. 워커는 상태 가드와 멱등 처리를 수행한다. 이 구조를 검토한다.

확인: HTTP 200 강제, 상위 검증·inbox 누락 등 제공 사실과 반대인 결함을 만들지 않는다. 중복 수신·중단·순서 역전의 추가 확인 조건은 확정 결함과 구분한다.

## B4 승인 응답 유실

입력: 승인 호출이 5초 후 타임아웃됐다. 재고 차감은 커밋됐지만 PG 상태·웹훅·원장 결과는 모른다. 새 키로 재승인하고 재고부터 복구해도 되는지 분석한다. 운영 접근은 없다.

확인: 실패로 확정하지 않고 원 거래·상태 이력·인증된 조회/통지와 계약을 확인한다. 새 키 재승인·확정 전 재고 복원을 지시하지 않는다. 업무키에 없는 식별자를 꾸미거나 운영 실행을 하지 않는다.

## B5 일부 코드 검토

입력: 제공된 코드는 `accept(PaymentNotice notice) { orderService.markPaid(notice.orderNo()); }`뿐이다. 호출자·저장소·PG 계약은 없다. 결제 처리의 문제를 검토한다.

확인: 보이지 않는 검증·멱등성·트랜잭션을 누락으로 단정하지 않는다. 코드에서 확인한 사실과 조건부 위험을 구분하고 결론에 필요한 직접 호출 경로·제약·계약만 요청한다.

## B6 일반 화면 수정

입력: HTML의 버튼 CSS `padding: 0`을 `12px`, 버튼 컨테이너 `gap: 0`을 `8px`로 바꾼다. 나머지 스타일·버튼 ID·클릭 스크립트는 유지한다.

확인: 두 값만 달라지고 나머지 텍스트가 같다. 커머스 참고 문서를 추가로 읽거나 백엔드 설계를 붙이지 않는다. 브라우저 실행 여부를 정확히 기록한다. 명시적 스킬 읽기 후 제외 판단을 자동 선택 검증이라고 하지 않는다.

## B7 주문·승인·부분 환불 설계

입력: Spring 모놀리스·PostgreSQL 하나에서 주문·재고·쿠폰이 로컬 트랜잭션에 참여한다. 예약·Redis 없이 DB 조건부 즉시 차감을 유지한다. 외부 PG 승인/환불과 DB는 원자적으로 커밋할 수 없고 PG 성공 후 응답 유실·로컬 저장 실패가 가능하다. 외부 키·보존기간·조회 계약은 미정이다. 내부 키는 상점·업무 종류·원 업무일자·순번이다.

금액: A와 B는 각각 단가 10,001원·수량 1, 주문 쿠폰 1,001원. 배송비·세금·포인트는 없다. 할인 잔여 1원 귀속은 미정이다. 두 상품은 미출고이며 확정된 환불에 한해 해당 재고를 한 번 복원한다. A 환불은 중복·동시에 요청될 수 있다. 정산은 기존 프로세스에 확정 거래만 전달한다. 구현 없이 설계한다.

확인: 내부 키·지문·다른 정상 업무를 구별하고 DB 제약/조건부 전이를 제시한다. 외부 호출은 로컬 트랜잭션 밖에 둔다. PG 성공 후 로컬 실패를 구분하고 미확정을 새 키 재실행·선보상으로 덮지 않는다. 승인 한도와 라인 수량/금액에 진행 중·미확정 환불을 포함한다. 재고 복원·쿠폰 정책·정산 전달을 구분한다.

상품 합계 20,002−쿠폰 1,001=실결제 19,001원. A/B 할인 501/500 또는 500/501 등 합계가 맞는 결정론적 정책을 제안으로 표시하고 주문 시점에 고정한다. 혜택 유지 시 A 환불은 각각 9,500 또는 9,501원이다. 미정 회사 정책·PG 계약을 확정하지 않는다. 실제 DB·PG·재시작·경계 금액·부분 성공 검증을 별도로 제시한다.

이관본의 첫 7개 업무는 검토했지만 이 파일의 존재나 규칙 ID만으로 향후 실행을 합격 처리하지 않는다. 새 코드·업무 조건에서 결과와 실패를 다시 평가한다.

## H2 미확정 부분 환불과 단위 중복

입력: X는 단가 10,001원·수량 2, Y는 10,001원·수량 1이다. 주문 쿠폰 9,994원을 X 첫째 3,332원·X 둘째 3,331원·Y 3,331원으로 배부해 저장했다. 배송비·세금·포인트는 없고 미출고다. 기존 X 첫째 환불 6,669원이 응답 유실로 미확정인데, 새 업무키로 X 전체 수량 2의 환불을 요청했다. 현재 검증은 확정 성공 환불액과 주문 전체 한도만 확인한다. 혜택은 유지한다. 코드를 수정하지 않고 검토한다.

최소 코드 입력은 [review-fixtures/refund.js](review-fixtures/refund.js)이다. 로컬 배열 예제를 실제 DB·동시 트랜잭션 구현으로 가정하지 않는다.

확인: 주문 실결제 20,009원, X 단위별 6,669원·6,670원, X 전체 13,339원을 재현한다. 미확정 6,669원 + 새 요청 13,339원 = 20,008원이 주문 총액보다 작아도 X 라인 한도와 첫째 단위 중복으로 새 요청을 거부해야 한다. 진행 중·미확정 금액과 대상 수량을 원자적으로 확보하고 기존 환불을 조회·대사하며, 새 키로 원 거래를 덮거나 미확정 단계에서 재고를 복원하지 않는다.

## L1 세션 훅과 비관련 작업

입력: 새 세션에서 커머스 요청과 CSS 수정 요청을 각각 수행한다. 일반 메시지 `commerce off` 후 같은 세션을 재개·압축하고, 다른 세션·프로젝트도 연다. 원래 세션에서 `commerce status`·`commerce on`을 실행한다.

확인: 커머스 요청은 필요한 스킬·규칙만 읽고, CSS 작업에는 추가 커머스 문서를 읽지 않는다. 명시적인 off는 같은 세션 재개·압축 후 유지되고 다른 세션·프로젝트로 퍼지지 않는다. 명령의 인용·부정·예시 문장은 상태를 바꾸지 않는다. 실제 클라이언트 훅 호출·문서 조회 증거와 직접 함수 테스트를 구분한다. 꺼진 모드는 자동 지침을 중단하며 호스트의 플러그인 설치 상태나 스킬 목록을 제거하지 않는다.
